# 0010 - Agent-harness images move into Cratis.AI, publish to Docker Hub

## Status

Accepted

## Context

`ai-consolidation-plan.md` Section 5.6 calls for `Direct/Source/AgentHarnesses/` - the three Docker
images (`Dockerfile.base`, `Dockerfile.claude`, `Dockerfile.pi`), `entrypoint.sh`, the `for_entrypoint/`
fixtures, `pi-extensions/`, the vendored `skills/`, and the `progress-mcp-server.mjs` MCP server - to
move wholesale into `Cratis.AI/Source/AgentHarnesses/`, since nothing in any of it is Direct-specific
in what it *builds*: it is a coding-agent toolchain image, not a Direct feature. The plan flagged the
registry target as an open risk (#7) - Direct publishes today's images to `ghcr.io/cratis` as
`direct-worker-base`/`direct-worker-claude`/`direct-worker-pi`, but the original brief called for
Docker Hub. The owner has now decided: Docker Hub, as `cratis/ai-agents`, `cratis/ai-agents-claude`,
`cratis/ai-agents-pi`.

## Decision

- Move `Source/AgentHarnesses/` into `Cratis.AI` unchanged in substance - the 301-line `Dockerfile.base`
  with its pinned-digest bump procedure, the 73/37-line Claude/Pi derivatives, the 1,539-line
  `entrypoint.sh`, the `for_entrypoint/*.sh` fixtures, `pi-extensions/`, the vendored Claude Skills
  under `skills/`, and `progress-mcp-server.mjs` all move as-is. `node_modules/` (gitignored in Direct)
  is regenerated by `npm ci`, not carried across.
- Rename every *publishing identity* reference from Direct-specific to product-neutral: the three
  image names (`cratis/ai-agents[-claude|-pi]`), the two standalone npm package names
  (`direct-worker-progress-mcp` → `cratis-ai-agent-progress-mcp`, `direct-worker-pi-extensions` →
  `cratis-ai-agent-pi-extensions`), the `[direct-worker]` log-line prefix in `entrypoint.sh` and the
  two `for_entrypoint/*.sh` scripts that echo it, and the handful of Dockerfile/package.json comments
  that described the image as Direct's own.
- Publish to Docker Hub, not `ghcr.io` - the base image first (`cratis/ai-agents:$VERSION`, plus
  `:latest` outside a prerelease), then both derivatives built `FROM` the tag this same run just
  pushed (never a stale `latest`), so a prerelease still produces internally-consistent derivatives.
  Uses `docker/setup-buildx-action` + `docker/login-action` (both pinned to full commit SHAs, matching
  this repository's own policy) reading the `DOCKER_USERNAME`/`DOCKER_PASSWORD` Cratis-organization
  secrets (already provisioned, visibility: all - the same two Studio's own `publish.yml` already logs
  in to Docker Hub with), and the same
  `docker-build-push-retry.sh` retry wrapper Direct already uses (its buildx-session-timeout reasoning
  is registry-agnostic, so it moved unchanged).
- The PR-time `verify` job gained Direct's own harness checks verbatim: shellcheck on `entrypoint.sh`
  and every `for_entrypoint/*.sh`, the progress-MCP-server's own `npm test`, and running every
  `for_entrypoint/*.sh` fixture (self-contained, hermetic, no live Docker build - these check the
  shell logic, not the image). None of this builds an actual image on every PR; only a real release
  run does, matching Direct's existing split between `build.yml` (fixtures only) and `publish.yml`
  (the real image build).
- `verify-published` now also fails the release if `publish-agent-harnesses` did not succeed, holding
  the harness images to the same "did the thing that has to ship actually ship" bar as the NuGet/npm
  pair - a product left pointing at a Docker tag Cratis.AI silently failed to push is a worse failure
  mode than a loud CI red.

## What deliberately did not move tonight

- **The `DIRECT_*` environment-variable contract inside `entrypoint.sh` is unchanged** - all ~31
  variable names (`DIRECT_WORK_ID`, `DIRECT_CALLBACK_URL`, `DIRECT_HARNESS`, `DIRECT_PROVIDER`, and so
  on) still read exactly what they did in Direct. Renaming this contract to something product-neutral
  (e.g. an `AGENT_*` prefix) is real, valuable work the plan gestures at ("the callback contract...
  moves into the package as the harness↔host protocol") but does not mandate as part of this move, and
  it is cross-cutting in a way the image move is not: every writer of these variables
  (`Direct/Source/Direct/Work/Workers/WorkerEnvironment.cs`, ~30 assignments) and every reader inside
  `entrypoint.sh` would need to change together, in lockstep, with no partial state that still works.
  Doing that in the same breath as relocating the images risks getting both half right. Tracked as
  follow-up work, not done here. Until it happens, Studio adopting this harness system means either
  living with the `DIRECT_*` names too or that follow-up landing first.
- **`Direct/Source/Direct/Work/Workers/WorkerEnvironment.cs` itself stays in Direct.** It is not a
  generic worker-runtime concern - it is Direct's own orchestration, built entirely from Direct's own
  domain state (`WorkItem`, `Group`, `Repository`, `Alert`, `ScheduledChain`, `ConfiguredGitIdentity`,
  content-creation settings). What content goes into the environment dictionary a job launches with is
  inherently product-specific; only the mechanics of launching and monitoring a container from that
  dictionary are generic. This matches the pattern already established for `ISecretProtector`,
  `IAIAlerts`, and `IAIUsageAttribution` elsewhere in this migration: the seam lives in the package,
  the product-specific implementation stays where the domain knowledge already lives.
- **`Direct/Source/Terminal/Dockerfile` stays in Direct** - explicitly out of scope per the plan; it is
  a read-only repository terminal, a different image for a different purpose, not a harness derivative.

## Consequences

- Docker Hub publishing uses the `DOCKER_USERNAME`/`DOCKER_PASSWORD` organization secrets, not a
  repository-level pair - no `Cratis/AI`-specific secret provisioning was needed. An earlier version
  of this PR assumed repository secrets named `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` did not exist and
  needed bootstrapping (the same shape `NPM_TOKEN` went through for `@cratis/ai`'s first publish,
  decision 0004's history) - that assumption was wrong. The organization secrets already exist, are
  already proven working (Studio's own `publish.yml` logs in to Docker Hub with exactly these two
  names), and are visible to every repository in the organization, `Cratis/AI` included. The workflow
  was corrected to use the real names once this was discovered.
- Direct's own `build.yml`/`publish.yml` still build and push the old `ghcr.io/cratis/direct-worker-*`
  images until Direct's own migration PR (plan Section 5.7) removes that job and repoints its
  deployment at `cratis/ai-agents-claude`/`cratis/ai-agents-pi`. Until that PR merges, the two image
  families exist in parallel, which is intentional - nothing about Direct's running deployment changes
  the moment this package starts publishing its own images.
