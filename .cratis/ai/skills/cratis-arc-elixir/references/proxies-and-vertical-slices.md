# Proxies and vertical slices

## Contents

- Vertical slices
  - Group slices into sub-features, and keep an integration beside what it serves
  - A read model owns its artifacts
  - Name things by their ids

Proxy generation is opt-in. Add the compiler and every `mix compile` regenerates the
TypeScript for commands and queries:

```elixir
# mix.exs
compilers: Mix.compilers() ++ [:arc],
arc: [application: MyApp.Arc, output: "assets/src/arc"]
```

`mix arc.gen.proxies` runs it directly: `--application`, `--output`, `--layout`, `--check`
(write nothing; fail if out of date, for CI) and `--no-remove-stale`.

- One file per artifact plus an `index.ts` per folder, deterministic: generating twice gives
  identical bytes.
- Every generated file starts `// @generated by Cratis. Source: <module>. Hash: <sha256>`. **A
  file without that marker is never overwritten or removed.**
- Enums, nested lists and derived types are not generated.
- The identity details type is generated, for `useIdentity`.

## Vertical slices

### Group slices into sub-features, and keep an integration beside what it serves

A feature that holds more than about six slices is usually several features. Look for these seams
before adding the next slice, and review them whenever a feature grows:

- **One noun, many verbs.** The slices that act on one thing (`rotating`, `revoking_previous`,
  `expiring_previous`, `retiring`) belong together in a sub-feature named for the
  thing (`secrets/`), not spread across a flat feature.
- **A reactor belongs with the facts it reacts to.** An automation that retires a secret after it was
  revoked lives in `secrets/`, not in a folder named for the third party it calls (`ory/`). A third
  party is an integration detail of the sub-feature, not a feature of its own; put its
  behaviour, adapter and stand-in in the sub-feature (or a shared folder when several use it).
- **Mirror the lifecycle.** Slices that detect, adopt and revert one kind of drift sit together.
- **A reactor and a view are slices too.** A reactor that records nothing is invisible in the event model.
  Have it record the fact that its effect happened (`SecretRetiredInOry`), so the automation shows
  what it produced.

The folder is the namespace: `Prism.Access.Api.Secrets.Rotating` is the slice
`Rotating` of the sub-feature `Secrets`. Arc's structure and event model show each
sub-feature as a feature of its own, so the grouping is what readers and tools see. Keep
`segments_to_skip` equal to the segments above the module.

### A read model owns its artifacts

A view slice has one file, named for its read model, holding everything the read model needs:

```text
viewing/listing/
  credential_listing.ex      the read model, its projection (or reducer) and its queries
  page.ex, page.html.heex    the page that shows it
  for_credential_listing/    its specs
```

Inside, the read model's module nests what it needs (`Credential`, then its projection, then its `Queries`),
the way a command shares a file with its events. Do **not** make files or folders named for a technical function
(`queries.ex`, `reducer.ex`, `projection.ex`, `read_models/`): the folder is the slice and the file is the read
model, so a reader finds the whole view in one place and the event model draws one box.

**Prefer a projection over a reducer.** Build the read model with the `Cratis.Chronicle.Projections` DSL
(`from/2`, `join/2`, `children/2,3`, counters). Use a reducer (`Cratis.Chronicle.Reducers.Reducer`) only when a
projection cannot express the transition (branching on prior state, calculations, guards over the previous
document) and say why in the read model's `@moduledoc`. A reducer is code you own and run; a projection is
declarative and the kernel can replay and diagram it.

### Name things by their ids

A command is `use Cratis.Arc.Command, id: "rotate-secret"`, an event type has an `id:`, a reactor has an
`id:` and a read model may have one. That id is the name: Arc shows `RotateSecret` in the structure and
the event model (`display_names:` on the Arc application picks `:pascal_case`, `:kebab_case`, `:as_declared`
or a function), so never rely on the last module segment as the name.

Organize by feature, not by layer: the Elixir, the generated proxies and the React page of
one feature share a folder. This matches the .NET guidance.

```text
lib/samples/ticker/
  ticker.ex  queries.ex  clock.ex      # backend
  Ticker.ts  Observe.ts  index.ts      # generated
  TickerPage.tsx                       # written by hand
```

```elixir
arc: [application: Samples.Arc, output: "lib", layout: :colocated]
```

`layout: :colocated` writes each proxy in the folder of the `.ex` file that defines its module,
relative to `output`; two modules in one file share a folder; a module whose source is
outside `output` falls back to a namespace-mirroring folder. Imports between proxies are
relative and generated. The default `:namespace` layout mirrors the module namespace
under `output` after `segments_to_skip`.

Make the tooling see both: Mix and the Phoenix reloader ignore `.ts` and `.tsx`, but
**`package.json` and `node_modules` must sit above `lib`** so a slice finds `@cratis/arc` by
looking upward, and the TypeScript and bundler config must include `lib`. Keep the app shell
(`index.html`, providers, the page that picks a slice) in its own folder.

Commit the generated files so a pull request shows the contract change beside its cause, and
run `mix arc.gen.proxies --check` in CI. What several slices share (a concept, a shared read
model) lives in a shared folder; slices reach each other through commands, queries and contracts,
never internals.
