# Coordinate delivery of several accepted slices

1. Make one written brief per accepted slice. Record the shared integration branch, the worker's branch/worktree, exact owned files and contracts, dependencies, observable acceptance criteria, the gate, and where and how to return the result. Distinguish backend and frontend work in the brief when a generated contract connects them. If `cratis-orchestration-lanes` is installed, reuse its lane-brief template; do not add lanes or leases just to delegate within a single session.
2. Order the briefs by dependency. Run only independent backends in parallel: if slices share files, events or a contract that one changes and the other consumes, serialize them. Keep one writer per worktree. Start at most two workers at a time unless the operator sets a different concurrency limit. If no isolated worker is available, run the same briefs serially.
3. Integrate completed backends on the shared branch and build the candidate. Where the UI consumes generated Arc proxies, follow `cratis-arc-generate-proxies` on that candidate. Release the frontend work only after the backend build and any proxy regeneration pass; frontends must start from that integrated contract, not a stale proxy or a worker's draft.
4. Have each worker return its status (complete, partial or blocked), changed files, exact checks and outcomes, and what remains. Stop and escalate any required change outside its ownership or an unresolved contract. Report partial delivery rather than stubbing a handler or silently dropping an acceptance case.
5. Review the integrated candidate with independent code, security and performance reviewers. Use `cratis-engineering-review-rounds` when installed and follow the `review-reports` rule when combining their reports. Keep each review's scope and evidence gaps. Missing or failed reviews are not approval.
