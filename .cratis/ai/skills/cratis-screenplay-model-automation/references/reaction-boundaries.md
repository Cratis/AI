# Decide what one reaction can promise

Start with one occurrence. An event reaction sees a recorded fact; its command may still have to decide whether acting is allowed **now**. A reaction is not by itself a lifecycle: use a state machine to follow an entity's lifecycle facts, or model a workflow when the process itself owns waits, deadlines and human work. A repeated entry can repeat its effects.

**Whose authority?** Declare `runs as system` once directly on the reaction, not on an individual trigger. Its declared roles apply to the commands it invokes across triggers. It does not supply arbitrary user claims, change the original caller or turn a direct `produces` into an authorized command. Without the declaration the invocation has no caller in the reference evaluator. If two triggers need different privileges, separate their responsibilities rather than giving both the union of roles.

**Whose decision?** If creating a welcome depends on whether an author is still eligible, pass the addressed author to the command and let the command protect its own decision read. Declaring a trigger `reads` does not make direct production from a stale read safe. An invocation-only reaction cannot map a read alias as a portable trigger value. Hiding the read in an opaque body does not establish protection either. For an event trigger, `$eventSourceId` identifies the triggering stream, not the caller; use it only when that is the desired command target.

**Which effects commit together?** At the application root, `reaction batches atomic` groups the direct productions of one trigger occurrence. Each invoked command decides independently. A selected refusal branch that produces facts has its own batch. Do not promise to undo an earlier accepted command when a later invocation refuses. Name the business refusal (authorization, validation or the intended constraint) that a branch may handle. A concurrency conflict or an unavailable store is not a business denial: leave it visible for retry or investigation rather than acknowledging it.

For a work list, project an opening fact such as `DirectoryWelcomeRequested` to a pending item. An invocation asks for the work; remove the item only on the agreed completion or cancellation fact. If the provider refuses or delivery is uncertain, keep the item pending or visibly in need of reconciliation according to the owner's decision. A row in the work list is not evidence a worker ran. Conversely, if registration itself is the complete business fact and nobody owes another action, do not invent a worker to publish a duplicate fact.

Check a normal occurrence, the named refusal and redelivery of the original fact. On redelivery, compare new effects without appending the trigger again. A successful check of this boundary does not prove a downstream message was delivered.
